# Phase 1 Final Analysis

Date: 2026-07-05

Scope: unstaged changes that complete the Phase 1 local inference vertical slice. This analysis focuses on how the new and changed files relate to each other in the program flow rather than line-by-line implementation detail.

## Summary

This pass turns the Phase 1 inference scaffold into a working local GGUF chat loop.

At startup, the app still loads config and bootstraps storage, then starts the coordinator and TUI. The coordinator now loads the configured model through the persistent inference worker. When the user submits a prompt, the prompt is persisted as a user message, forwarded to the worker, generated by the real `llama-cpp-2` backend, streamed back as token deltas, rendered by the TUI, and persisted as an assistant message when generation finishes.

Cancellation is now part of that same loop. The TUI sends cancellation while work is in flight, the coordinator signals the backend cancellation token, and storage marks the active exchange as cancelled so cancelled messages are filtered out of future history loads.

## Dependency and Boundary Changes

### `Cargo.toml` and `Cargo.lock`

The workspace now pins `llama-cpp-2 = "=0.1.150"`.

That dependency is attached only to `crates/llama-backend`, preserving the architecture rule that all llama.cpp-specific types stay inside the backend crate. `Cargo.lock` expanded because `llama-cpp-2` pulls in the native llama.cpp sys crate and its build-time dependencies.

### `crates/core/src/lib.rs`

`core` now owns shared, serializable configuration and model runtime types:

- `AppConfig`
- `PathConfig`
- `UiConfig`
- `InferenceConfig`
- `InferenceDefaults`
- `RetrievalConfig`
- `IndexingConfig`
- `ChunkingConfig`
- `ModelSpec`
- `RuntimeModelConfig`

These types describe application-wide configuration and backend-neutral runtime inputs. They are used by multiple crates, so moving them into `core` removes the need for callers to depend on `storage` just to name config shapes.

In the flow, `storage` still reads and writes config files, but it deserializes into `core::AppConfig`. `model-manager` plans runtime settings using `core::ModelSpec` and `core::RuntimeModelConfig`. `inference` re-exports these runtime types so existing worker protocol code can continue to import them from the inference boundary.

### `crates/inference/src/lib.rs`

`inference` no longer defines `ModelSpec` and `RuntimeModelConfig` directly. It re-exports them from `core`.

The crate remains the backend-neutral protocol layer. It still owns:

- `InferenceBackend`
- `GenerateRequest`
- `WorkerCommand`
- `GenerationEvent`
- `CancellationToken`
- `TokenSink`
- `InferenceError`

In the overall flow, `app` sends `WorkerCommand`s to the inference worker, the worker calls an `InferenceBackend`, and backend output returns through `GenerationEvent`.

### `crates/model-manager/Cargo.toml` and `crates/model-manager/src/lib.rs`

`model-manager` no longer depends on `inference`.

`ResourcePlanner` now imports `ModelSpec` and `RuntimeModelConfig` from `core`. This restores the intended boundary: model management can reason about model metadata and runtime planning without depending on the inference protocol crate.

## Backend Flow

### `crates/llama-backend/Cargo.toml`

`llama-backend` now depends on `llama-cpp-2`.

This is the only crate in the workspace that imports llama.cpp binding types.

### `crates/llama-backend/src/lib.rs`

`LlamaBackend` is now a real `InferenceBackend` implementation.

It owns:

- `llama_cpp_2::llama_backend::LlamaBackend`
- the loaded `LlamaModel`
- the active `ModelId`
- the active `RuntimeModelConfig`

The backend does not store a long-lived llama context. Instead, it creates a fresh `LlamaContext` for each generation request. This avoids a self-referential Rust struct because `LlamaContext` borrows the loaded `LlamaModel`.

The main generation path is:

1. `load_model` initializes llama.cpp, applies mmap/mlock settings, and loads the configured GGUF file.
2. `generate_stream` tokenizes the prompt with BOS, validates it fits the configured context, creates a context, decodes the prompt batch, and builds a sampler from the request generation settings.
3. The decode loop samples one token at a time, checks EOS and cancellation, converts tokens to text bytes, sends `GenerationEvent::TokenDelta`, decodes the sampled token back into the context, and continues until `max_tokens`, EOS, or cancellation.
4. A `GenerationSummary` reports model ID, generated token count, context token usage, throughput, stop reason, and duration.

The implementation currently treats the prompt text as already assembled. It does not apply model chat templates yet; that remains future prompt/mode work.

### `crates/llama-backend/tests/streaming.rs`

This new integration test is ignored by default because it requires a real GGUF model path.

When run with `LORELM_TEST_MODEL_PATH`, it verifies the real backend can:

- load a GGUF model
- generate a short response
- emit at least one `TokenDelta`
- return a non-cancelled summary
- unload the model

It gives Phase 1 a concrete manual smoke-test path without making CI or normal local tests depend on a large model artifact.

## Coordinator and Storage Flow

### `app/src/coordinator.rs`

The coordinator now persists enough information about the active exchange to support soft-delete cancellation.

`ActiveGeneration` now tracks:

- conversation ID
- persisted user message ID
- assistant sequence number
- mode ID
- streamed assistant content accumulated so far
- optional model ID

Normal generation flow:

1. `start_generation` persists the user message and records its ID.
2. The coordinator sends `WorkerCommand::Generate` with a `CancellationToken`.
3. `TokenDelta` events append to the in-memory assistant buffer and are forwarded to the TUI.
4. `Finished` creates and persists the assistant message using the accumulated streamed text, then forwards `GenerationFinished`.

Cancellation flow:

1. `Command::CancelGeneration` now only signals the cancellation token. It does not immediately tell the TUI that generation is cancelled.
2. The backend observes cancellation and returns a cancelled summary, or the worker sends `GenerationEvent::Cancelled`.
3. `cancel_active_generation` marks the already-persisted user message as cancelled.
4. If any assistant text had streamed, it persists that partial assistant message with `MessageStatus::Cancelled`.
5. The TUI receives `GenerationCancelled` only after the worker/backend acknowledges cancellation.

This keeps UI state aligned with backend state and ensures cancelled exchanges are not included after restart.

### `crates/storage/src/lib.rs`

`storage` no longer defines shared config structs. It imports `AppConfig` from `core`, but remains responsible for config file I/O.

The new `update_message_status` method updates a persisted message status and refreshes the parent conversation timestamp. The coordinator uses it to mark the active user message cancelled.

The existing history load behavior already excludes `status = 'cancelled'`. A new storage test verifies that a message changed from complete to cancelled is filtered from loaded application state.

## TUI Flow

### `crates/app-tui/src/lib.rs`

The TUI already knew how to render streamed assistant text from `TokenDelta`; this pass tightens input and state behavior around that path.

Prompt-focused `Tab` now inserts a tab instead of cycling focus, and `BackTab` does not cycle focus while the prompt is focused. This matches the intended prompt editing model: the user leaves prompt focus with `Esc` before navigating panels.

Cancellation can now be requested from `Preparing`, `Retrieving`, or `Generating`. The TUI moves to `GenerationState::Cancelling` and waits for a `GenerationCancelled` event before returning to `Idle`.

New TUI tests cover the prompt-focused `Tab` and `BackTab` behavior.

## Program Flow After This Pass

1. `main` resolves XDG paths, opens storage, loads `core::AppConfig`, bootstraps the default workspace/conversation, estimates RAM, and starts the TUI plus coordinator.
2. `Coordinator::new` starts the persistent inference worker and loads `paths.model_path` if configured.
3. The inference worker owns one `llama_backend::LlamaBackend` instance.
4. `LlamaBackend::load_model` loads the GGUF file and stores runtime config.
5. The user submits a prompt in `app-tui`.
6. The TUI sends `Command::SubmitPrompt` and moves to `Preparing`.
7. The coordinator persists the user message, records active generation metadata, and sends `WorkerCommand::Generate`.
8. The worker calls `LlamaBackend::generate_stream`.
9. The backend streams `GenerationEvent::TokenDelta` through the channel.
10. The coordinator forwards token deltas as `AppEvent::TokenDelta`; the TUI appends them to `streaming_response` and renders incrementally.
11. On success, the coordinator persists the assistant message and forwards `GenerationFinished`.
12. On cancellation, the coordinator marks the exchange cancelled and forwards `GenerationCancelled`.

## Decisions Made In This Pass

These are the decisions worth considering for the Architectural Decision Log.

### Decision Candidate 1 - Phase 1 Scope Is Local GGUF Chat, Not Document Q&A

- **Date:** 2026-07-05
- **Decision:** Completed Phase 1 as a local GGUF chat loop with streaming and cancellation. Document import, chunking, FTS retrieval, citations, and document Q&A remain in Phases 2 and 3.
- **Replaces:** The broader “First Vertical Slice” note in `docs/implementation-plan.md` that lists document import, chunking, FTS, and context prompt assembly by the end of Phase 1.
- **Reason:** `docs/progress-tracker.md` already assigns document import to Phase 2 and document Q&A retrieval to Phase 3. Keeping Phase 1 focused avoids pulling later-phase scope forward before the local inference foundation is stable.

### Decision Candidate 2 - Config and Runtime Planning Types Belong In `core`

- **Date:** 2026-07-05
- **Decision:** Moved shared config shape and backend-neutral model runtime types into `core`.
- **Replaces:** The prior implementation where `storage` owned config structs and `model-manager` depended on `inference` for runtime planning types.
- **Reason:** These are shared serializable/domain types, not persistence-only types. Moving them to `core` restores crate boundaries: `storage` handles I/O, `model-manager` handles planning, and `inference` handles worker/backend protocol.

### Decision Candidate 3 - `llama-cpp-2` Is Pinned At `0.1.150`

- **Date:** 2026-07-05
- **Decision:** Added `llama-cpp-2 = "=0.1.150"` as the real local inference backend binding.
- **Replaces:** The prior `llama-backend` stub that only checked model path existence and returned “generation is not implemented yet.”
- **Reason:** Phase 1 requires actual local GGUF inference. Pinning the binding keeps a fast-moving llama.cpp API stable for this project.

### Decision Candidate 4 - Create A Fresh Llama Context Per Generation

- **Date:** 2026-07-05
- **Decision:** `LlamaBackend` stores the initialized backend and loaded model, but creates a new `LlamaContext` for each generation request.
- **Replaces:** No explicit documented behavior; this is an implementation choice within the `llama-backend` boundary.
- **Reason:** `LlamaContext` borrows `LlamaModel`, so storing both in the same backend would require a self-referential structure. Creating a fresh context per request keeps ownership simple and safe for Phase 1.

### Decision Candidate 5 - Streaming Deltas Are The Source Of Final Assistant Text

- **Date:** 2026-07-05
- **Decision:** The backend streams generated text through `GenerationEvent::TokenDelta`; the coordinator accumulates those deltas and persists the assistant message on `GenerationFinished`.
- **Replaces:** No final-text event was added to `GenerationEvent`, and `GenerationSummary` remains metadata-only.
- **Reason:** Phase 1 needs streaming output, and using token deltas as the single text path avoids duplicating assistant content in a second terminal event.

### Decision Candidate 6 - Cancellation Is Acknowledged By The Worker Before UI Completion

- **Date:** 2026-07-05
- **Decision:** `CancelGeneration` signals the cancellation token but does not immediately emit `GenerationCancelled`; the coordinator waits for worker/backend acknowledgement before returning the TUI to `Idle`.
- **Replaces:** The previous coordinator behavior that sent `GenerationCancelled` immediately after receiving the cancel command.
- **Reason:** This keeps the UI state synchronized with actual inference state and gives the coordinator one place to mark persisted messages cancelled.
